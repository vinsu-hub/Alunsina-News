# Wave 2a: Story Pitch / Claim Board + Admin: backend foundation (Codex)

Read docs/tasks/_common.md, docs/DECISIONS.md, and **docs/reference/PITCH_BOARD_SPEC.md** (the feature spec; implement its rules exactly). You are the only worker running; two more workers build on your API right after you (admin UI, public board), so keep the API clean and documented.

## Context / decisions (from the product owner)
- **No contributor logins.** The site owner manages everything through an **admin panel**. Pitches are posted and status changes recorded by the admin *on behalf of* a verified contributor ("self-reported by the journalist, recorded by admin"). Still no per-pitch approval step of any kind.
- **Admin auth:** single-tenant. `ADMIN_PASSWORD` (plain in env, compared with `timingSafeEqual` on SHA-256 digests) + `ADMIN_SESSION_SECRET` (HMAC-SHA256 signed, httpOnly, secure, sameSite=lax cookie, 12h expiry). Login rate-limited (5 tries / 15 min / IP, in memory). Next 16 uses **`proxy.ts`** (not middleware): read `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md` first. Protect `/admin/**` and `/api/admin/**` in the proxy AND re-check the session inside every server action / route handler (defense in depth). `/admin/login` is public.
- **Pre-screen (Laya) is held-until-screened:** a pitch (at submission) and a published piece (at publish) get `screening_status = 'pending'` and are NOT publicly visible until `'passed'`. `'flagged'` items are never public; the admin sees the categories. There is **no manual pass/override** (that would be a per-story approval); the admin can only re-run the screen. The screen checks jailbreak/injection + harassment/threat/doxxing/targeted-defamation patterns only, never topic, viewpoint, or whether an official is named.
